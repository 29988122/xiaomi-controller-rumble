# 核心原始碼與手機韌體不相符時，如何補回手把震動

> v0.3.0 新增一次重開機與「動作」稍後設定。核心驅動不變，新服務與 FF 測試程式僅經軟體測試；安裝請依[目前說明](../README.zh-TW.md)，驗證範圍見[更新紀錄](../CHANGELOG.md)。

> 後續更新：v0.2.1 針對實際校正失敗，修正安裝時的就緒等待與錯誤提示；手機端安裝腳本檢查範圍見[更新紀錄](../CHANGELOG.md)。下文保留 v0.2.0 原始調查紀錄。

[English](writeup.md) · [專案首頁](../README.zh-TW.md)

## 1. 手把能操作，唯獨馬達不動

GameSir G8+ 以 DS4 藍牙模式連到 Redmi Note 12 Pro 5G（`ruby`）。系統能提供按鍵、搖桿介面，卻沒有手把震動。手機是 Android 14／HyperOS `OS2.0.8.0.UMOTWXM`，核心 `4.19.191-gdecc267868f3`，root 為 Magisk Alpha。前一輪串流延遲調查已讓使用者關閉 Low Latency Video；本次保持該設定，震動是另一個問題。

調查從真實輸入路徑開始，而不是從 root 管理器品牌推測：

```text
藍牙 HID → 核心內建 Sony 驅動 → Linux 輸入裝置 → Android 輸入框架
```

G8+ 呈現 `054C:05C4`，綁定 `sony`。`/proc/config.gz` 顯示 `CONFIG_HID_SONY=y`、`CONFIG_INPUT_FF_MEMLESS=y`，但沒有啟用 `CONFIG_SONY_FF`；手把輸入節點也沒有 `EV_FF／FF_RUMBLE`。缺少的是編譯時未納入的驅動功能，並不是取得 root 後就能切換的 Android 選項。

**我們不知道小米為什麼選擇這份設定。** 能確認的是出廠核心的設定與行為，不能替原廠猜測決策原因。同樣地，本次確認公開來源與這個韌體不完全相符，不能據此概括所有小米機型的開源狀況。

## 2. 先證明實體輸出通道可用

更換核心驅動前，先利用既有 `hidraw`，對指定手把發送短暫、低強度輸出。DS4 藍牙與 USB 封包不同：測試採用 78 位元組、ID `0x11` 的報告，保留既有回報間隔，只更新馬達，CRC32 涵蓋輸出前綴 `0xA2` 與前 74 位元組。強度限制在 80/255，附帶停止指令與 shell 結束／訊號清理。

測試要求一側一下、另一側兩下。`write()` 成功只表示軟體介面接受了資料，不能證明馬達運轉。使用者第一次沒注意到，重測後才確認兩側確實有震動。這證明該手把與手機內建藍牙能傳送這套輸出協定，尚未證明 Android 標準 FF 路徑可用。

`tools/device.py` 保留這個限定裝置識別碼的診斷工具。重連後 event／hidraw 編號可能改變，應重新辨識裝置，不可把 `/dev/input/event9` 或 `/dev/hidraw0` 當固定介面。

## 3. 替代的是什麼？程式在哪裡執行？

修補使用獨立編譯的 Sony 衍生驅動 `sony_g8ff`，在自己的編譯單位加入 `CONFIG_SONY_FF`。既有核心已包含它需要的通用 memoryless FF 實作。新驅動採用不同名稱，並拒絕指定藍牙識別碼及 VID:PID 以外的裝置。

```text
使用者空間的 root 管理器服務
  → 載入 sony_g8ff.ko
  → 將指定 HID 裝置從 sony 解除綁定
  → 將該裝置綁到 sony_g8ff

核心 FF 請求 → sony_g8ff → 藍牙 HID 輸出 → 手把馬達
```

`.ko` 是**核心空間程式**，不是使用者空間驅動。Magisk／KernelSU 的 shell 腳本在使用者空間負責管理。內建 `sony` 沒有被刪除或卸載，仍能服務其他裝置，也能用於復原。前提是相關匯流排與驅動可安全解除／重新綁定，而且替代模組真正相容。

新驅動保留 Sony 原本的主要輸入、觸控、動作感測、電池與燈號實作，移除時送出停止震動。管理程式保留藍牙回報間隔，停用時恢復原廠綁定。這是指定裝置的驅動接管，不是修改正在運作的核心設定旗標。

## 4. 來源很接近，卻不完全相同

公開的 `ruby-s-oss` 是較早的 Android 12 時期版本，不能因版本數字看似接近就假設相容。實機啟用了 MODVERSIONS、CFI、LTO，使用 Android Clang 11 r383902；因此建置也採用相同的編譯器版本，在 Linux x86_64 上產生 ARM64 模組。

選擇遠端 Linux 的原因是工具鏈相容性：精確匹配的預編譯 Clang 本身是 Linux x86_64 程式，本機 Mac 則是 macOS ARM64。Mac 另建 Linux 虛擬機也能做。這次已有 Linux 主機，使用專用 rootless 容器限制 CPU／記憶體，套件只裝在容器裡。

### 從現行韌體取得證據

唯讀備份當前 boot 分割區，核對手機與本機雜湊，解出核心，再以 `vmlinux-to-elf` 還原方便分析的 ELF 符號視圖。這是解讀既有位元組，不是還原原廠缺失的 C 原始碼。

**這一顆 ARM64 核心**的匯出表使用 16 位元組絕對位址項目，對應 4 位元組 CRC。擷取器檢查表格邊界、符號名稱／位置對應與數量，再得到 12,380 筆匯出符號。其他核心可能使用相對位址或不同布局；附帶工具是特定案例實作，遇到不符布局應停止，不能照抄偏移。

實機 `/proc/kallsyms` 的位址被遮蔽。調查沒有關掉這項保護，而是使用私下保存的 boot 備份作為證據。

### 第一種 ABI 探測方法造成誤判

早期做法把多個匯出函式宣告放進同一個編譯單位，產生版本 CRC。這個人工探測檔能看到的型別定義，與真正匯出函式的來源檔不同，因而出現假性的 CRC 不一致。CRC 必須放回正確的編譯脈絡解讀。

改進後直接編譯**真正實作並匯出函式的核心來源檔**，收集它們產生的 `.symversions`。問題因此變成：這份來源與設定，能否獨立描述出與出廠核心相同的匯出介面？

修正探測方法後，驅動需要的介面除了三個 power_supply 相關函式外都相符。我們沒有把原廠 CRC 硬填進不相符的物件檔，而是追查原因。

### 少掉的九個列舉項目

原廠二進位 `power_supply_attrs` 有 284 個屬性，公開標頭只有 275 個。屬性名稱及順序提供了九個新增列舉項目的證據：

- `MTBF_TEST` 後的 `ADAPTING_POWER`。
- `THERMAL_LIMIT_FCC` 後的 `BATT_SN`、`MAX_LIFE_VOL`、`MAX_LIFE_TEMP`、`OVER_VOL_DURATION`。
- `SHUTDOWN_DELAY` 後的 `FG_BATT_SN`、`FG_MAX_LIFE_VOL`、`FG_MAX_LIFE_TEMP`、`FG_OVER_VOL_DURATION`。

確認屬性陣列布局與共用 callback 後，只修正**建置用標頭**，沒有修改手機的電源管理程式或 boot。部分既有 enum 與 sysfs 名稱原本就是別名，沒有為了字串一致而任意更名。

重新編譯真正的匯出實作後，三個 CRC 隨即吻合：

| 匯出符號 | 獨立計算後相符的 CRC |
|---|---|
| `devm_power_supply_register` | `0xf0588502` |
| `power_supply_get_drvdata` | `0xaf625b30` |
| `power_supply_powers` | `0x5cfe9ca7` |

這讓電池介面得以保留，但只構成這些介面的證據，**不表示已還原整份缺少的 vendor 原始碼**。

### 檢查最後的模組，不只看最初的相依符號

建置獨立計算出的 624 個匯出介面都與原廠相符，最終 `.ko` 所需的 61 個符號（含 `module_layout`）也全數吻合。連結過程可能加入編譯器產生的相依，因此不能只檢查 LTO 前的物件檔。

最終 ELF 的架構、匯入符號涵蓋範圍、每筆 `__versions`、vermagic 與 CFI 符號都經過檢查。核心版本後綴是在介面檢查後經由 Kbuild 設定，沒有直接修改二進位字串來繞過載入器。重新建置得到相同雜湊：

`4798bdc9521a0e68f63f5d430ab71122355f891aaf920aec9e01ecdcc4b09035`

MODVERSIONS CRC 不是完整的語意或記憶體安全證明。inline 行為、設定假設、內部結構、編譯器插樁與執行期間的物件生命週期仍可能有差異。版本字串相同更是遠遠不足，所以暫時載入與復原測試不可省略。

## 5. 暫時部署揭露了兩個值得記錄的錯誤

首次載入不設開機自動執行，只切換指定手把並檢查輸入能力。Android 出現震動輸入映射器。獨立的 ARM64 evdev 測試程式上傳有時間上限的 `FF_RUMBLE`，依序播放、停止、清除，使用者再次確認兩側馬達實際震動。最後版本的測試工具也檢查停止與清除的回傳值。

持久化前先驗證復原：切回 `sony`、卸載替代驅動，觀察 FF 消失；重新載入並綁定後，FF 恢復。

重連管理程式接著遇到競爭問題：HID 目錄與 `sony` 驅動連結已出現，但 probe 還沒建立 `bt_poll_interval`。把缺檔當成永久失敗會讓背景程序提早停止。修正後會等待原廠驅動的屬性就緒再接管，並加入針對未完成初始化狀態的回歸測試。

另一個問題來自測試時序：藍牙還在關閉途中就要求啟用，可能被誤認成驅動無法重連。等待狀態切換完成後才繼續，才能區分匯流排／藍牙生命週期與驅動問題。測試也要求輸出明確的成功標記，不只依賴可能被清理指令遮蔽的 ADB／shell 結束狀態。

修正後，連續三次真正的藍牙斷線／重連都確認新驅動綁定、FF 操作與原有 4 ms 間隔正常。

## 6. 持久化與驗證邊界

服務等待 Android 開機完成，再檢查韌體及模組雜湊、載入驅動並監看重連。鎖定機制避免重複背景程序，boot identity 用來辨識前一次開機留下的鎖。模組停用後恢復原廠綁定並卸載替代驅動。

開機測試前先確認 USB ADB 可用。實際重開機證明自動載入與接管成功；停用已安裝模組後能恢復原廠，重新啟用後 FF 恢復。boot 雜湊未變，SELinux 維持 Enforcing；最後擷取的核心紀錄中沒有發現 CFI 失敗、未知符號、oops 或 panic。

測過螢幕休眠／喚醒，不等於深度休眠壓力測試。看見原有輸入介面，也不等於逐一操作全部按鍵、感測器及應用程式。**使用者明確要求略過 Steam Link、遊戲延遲與 30 分鐘遊戲實測。** Android 暴露 FF 能力是必要條件，不是每款遊戲都能正確串流震動的證明。

公開 v0.2.0 ZIP 沿用完全相同的驅動，但安裝器改成選定唯一已連線手把，識別碼只保留在本機。公開安裝器接受自動化介面契約測試；手機保持原先驗證過的安裝，沒有重新安裝公開版或更換 root 管理器來宣稱相容。KernelSU、KernelSU Next 支援所需封裝／腳本介面，但沒有 KernelSU 實機驗證；其他 fork 仍未驗證。

## 7. 人類與後續 AI agent 可遵循的流程

1. **記錄實機基準**：機型代號、完整 ROM 指紋、核心版本／編譯器／設定、root 機制、HID 識別／綁定與 FF 能力。私下保存目前 boot 並核對雜湊，不猜 active slot。
2. **證明實體協定**：分辨 USB／藍牙封包，限制馬達強度與時間，送出停止指令，再由人確認。傳輸成功不等於馬達測試成功。
3. **先確認可行性**：模組載入／卸載、簽章政策、必要匯出函式、FF 相依、CFI／LTO、工具鏈與重新綁定能力。
4. **尋找可辯護的來源與韌體證據**：優先找完全相符的 vendor release；有足夠證據時才還原局部差異，記錄每個假設。
5. **獨立比對**：編譯真正的匯出實作，核對版本，檢查最後模組；無法解釋的差異就停止。不可把預期 CRC 直接填入未算出相同值的物件。
6. **暫時測試**：首次不自動載入，只接管一支手把、保留間隔，驗證介面、標準 FF 與原廠復原。
7. **驗證生命週期**：重連、睡眠／喚醒、應用程式、長時間使用、停用／移除、重開機；誠實記錄省略項目。持久化前確保復原途徑。
8. **發布範圍明確的 profile**：來源／工具鏈、雜湊、設定、ABI 證據與實測範圍。分享方法，不把未測機型列為已支援。

AI agent 應區分觀察與推論，並請使用者回報實體結果。相容性卡關時應停在證據不足的位置，不能把 root 權限當成憑空宣稱通過的理由。

## 8. 這個方法不夠用的情況

| 條件 | 下一步 |
|---|---|
| 禁止載入模組，或無法提供必要簽章 | 尋找正確建置／簽署的核心或支援的韌體途徑；本 ZIP 無法繞過政策。 |
| 缺少匯出符號或 FF 相依 | 確認能否單獨建置相依模組；否則可能需要更完整的核心修改。 |
| 來源不足以確認結構或 CFI 假設 | 取得相符來源與建置環境，或停止部署。 |
| 裝置不能安全重新綁定 | 研究其他驅動整合方式，不能假設所有內建驅動都可替換。 |
| 原始震動可用，但 FF／應用程式失敗 | 另查輸入框架與應用程式，不要反覆亂改藍牙封包。 |
| 考慮使用者空間橋接 | 若環境支援，hidraw 搭配虛擬輸入裝置是可能方向；但輸入與 FF 路由、重複裝置、感測器與 Android 辨識都是實質工作，本專案未實作。 |

取得相符來源、可靠建置與復原方式後，完整重編核心仍是合理選項。替代模組縮小了變更範圍，並沒有消除相容性要求。可重用的經驗是逐步縮小不確定性，直到特定修改有足夠證據，而不是強迫任意模組載入不透明的核心。
